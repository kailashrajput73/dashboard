# Post-row 21 Layer 1D: racks API parity

## Scope

Implement RTE-33–37 only on the PostgreSQL backend:

- `GET /api/racks`
- `POST /api/racks`
- `DELETE /api/racks/{rack_id}`
- `PUT /api/racks/{rack_id}/assign`
- `GET /api/racks/{rack_id}/products`

No product-group changes were made. Steps 1E–1G and Layer 2 remain out of
scope.

## Built

- Added the rack router and service using existing `racks` and `rack_slots`
  tables. API fields preserve Mongo casing: rack `rows`, `columns`, `slots`,
  slot `code` and `productId`, and `createdAt`.
- Rack creation trims and validates names and dimensions (1–26 rows,
  1–100 columns), rejects active case-insensitive name duplicates, and
  generates slots in row-major `A1`, `A2`, … order. It returns the rack with
  the complete slots array.
- Rack listing returns active racks sorted by name with active slots in
  row/column order. Rack products returns full catalog objects sorted by
  name, matching the Mongo service shape.
- Assignment accepts either a catalog `id` or `productCode`, checks that the
  rack, product, and slot exist, and returns
  `{rackId, rackName, slotCode, productId}`. It atomically clears an existing
  placement for that product, replaces the slot's former occupant and updates
  both `rack_slots` and the catalog rack fields. This fulfills TXN-15 in one
  transaction and also clears the replaced occupant's matching catalog
  location.
- Deletion returns `{deleted, id}`, returns 404 for a missing rack, and
  returns 409 when any active slot contains a product. As required by the
  PostgreSQL soft-delete policy, a deletable rack and its slots are soft
  deleted rather than physically removed.
- Added an Alembic migration for active, case-insensitive rack-name
  uniqueness. It checks existing active data and stops with a clear error if
  duplicate names would prevent the index from being created.
- Routes use PostgreSQL admin Bearer authentication. Reads permit the
  existing authenticated team roles; mutations require `admin`. Mongo routes
  are public; PostgreSQL uses its existing protected admin boundary.

## Mongo differences and remaining work

- PostgreSQL retains a rack row and its slot rows as soft-deleted records
  instead of Mongo's hard delete. Creating a rack with a previously deleted
  case-insensitive matching name reactivates the retained row and rebuilds
  the requested slots.
- Assignment is transactional and clears the slot's prior catalog occupant
  when its catalog rack fields match that slot; Mongo can leave those fields
  stale after replacement. It also permits `productCode` as an identifier,
  matching the documented post-baseline safer assignment behavior.
- The route itself has no rack-products web caller; the route is retained
  for RTE-37 parity. `RacksPage` consumes the rack list/create/delete/assign
  routes, and `PurchasesPage` consumes the rack list for its optional
  selection.
- No changes were made to purchase logic or the 1A–1C implementation.
- Generic audit logging remains deferred in `DB-STATUS.md`.
- PostgreSQL-backed integration, the 8001 UI flow, and optional Mongo
  comparison remain for user verification.
- No files were changed in `web/`, `frontend/`, or `backend_refactor/`.

## DB-STANDARDS.md check

1. **Tables:** No table was added. Existing tables have primary keys,
   timestamps, and nullable `deleted_at` fields.
2. **Relationships:** No FK changed. Existing `rack_slots.rack_id` and
   `rack_slots.product_id` are ID references with the existing cascade/set
   null behavior and indexes. Catalog's rack reference remains a real FK.
3. **Search/filter/sort indexes:** Existing rack name and slot/catalog
   indexes are retained. Added a partial case-insensitive unique rack-name
   index for active rows; its migration checks existing data first.
4. **Uniqueness:** Application duplicate checks and the partial unique index
   protect active rack names. Existing exact-name uniqueness remains.
   Existing slot-code and one-product-per-slot uniqueness constraints remain.
5. **Transactions:** Applicable to RTE-36. Slot replacement, old placement
   clearing, and both catalog rack-field changes run in one transaction.
   Create, delete, and rack restoration/slot synchronization are also
   transactional.
6. **Authentication/authorization:** All routes use the existing admin
   Bearer dependency. Reads permit `admin`, `store_manager`, and `staff`;
   rack writes require `admin`.
7. **Incoming-data validation:** Pydantic schemas define the required create
   and assignment fields. Service validation enforces trimmed rack names,
   dimension bounds, and rack/product/slot existence before database writes.
8. **Audit log:** Not applicable to reads. For writes, the generic audit log
   remains a documented deferred item in `DB-STATUS.md`; no audit mechanism
   was invented for this row.

## How to test

1. With PostgreSQL configured, apply migrations and start the backend on
   `127.0.0.1:8001`:

   ```powershell
   Set-Location C:\Users\Dell\Desktop\dashboard\backend
   .\.venv\Scripts\python.exe -m alembic upgrade head
   .\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8001
   ```

2. Point the web app's `VITE_BACKEND_URL` at
   `http://127.0.0.1:8001`, sign in as an admin, and open Racks. Confirm the
   list loads; create a rack and assign a product to a slot.
3. Confirm an occupied rack cannot be deleted. On Purchases, confirm the
   optional rack selector lists the created rack and exposes its slots.
4. Optional side-by-side comparison: make the same requests against Mongo on
   port 8000 and compare envelopes and payload fields.
